# 07. 예외 처리 및 보안 설계

관련 문서: [01 요구사항](01-requirements.md) · [05 API](05-api-spec.md) · [06 화면](06-screens-and-user-flow.md)

> 구체 라이브러리/서비스는 DEC-01~04, 06 확정 후 정한다. 여기서는 **요구되는 동작과 기준**을 정의한다. 수치는 **[제안]** 이다.

## 1. 예외 처리 설계

### 1.1 원칙
1. 사용자에게는 **이해 가능한 한국어 메시지 + 다음 행동**(재시도/로그인/뒤로)을 보여준다.
2. 내부 정보(스택, SQL, 서버 경로, 외부 API 키)는 응답/화면/로그 노출 금지.
3. 서버는 모든 에러를 **공통 에러 형식**(05 문서 §1.2)으로 반환하고 `requestId`를 포함한다.
4. 외부 API 장애가 사용자 조회에 영향을 주지 않는다 (자체 DB 서빙, NFR-AVAIL-01).
5. 변경 요청은 **멱등**으로 설계해 재시도를 안전하게 한다.

### 1.2 서버 측 예외 시나리오

| 영역 | 상황 | 처리 | 응답 |
|------|------|------|------|
| 입력 | 잘못된 쿼리 값(limit 범위, sort 값) | 검증 실패 처리 | 422 `VALIDATION_FAILED` + 필드 상세 |
| 입력 | 잘못된/위조된 cursor | 거부 | 400 `BAD_REQUEST` |
| 인증 | 토큰 없음/위조 | 거부 | 401 `UNAUTHENTICATED` |
| 인증 | access 만료 | 갱신 유도 | 401 `TOKEN_EXPIRED` |
| 인증 | refresh 재사용 감지(이미 회전된 토큰) | 해당 사용자 해당 계열 세션 전체 폐기 | 401 `REFRESH_TOKEN_INVALID` |
| 인증 | 로그인 반복 실패 | IP/계정 기준 지연·제한 | 429 `RATE_LIMITED` |
| 인가 | 타인 데이터 접근 시도 | 경로에 사용자 ID를 받지 않고 **토큰의 사용자만** 사용 (`/users/me`) → IDOR 원천 차단 | - |
| 리소스 | 없는 카드 ID | | 404 `NOT_FOUND` (보유 해제는 멱등 204) |
| 동시성 | 같은 보유 PUT 동시 요청 | 복합 PK + `ON CONFLICT DO NOTHING` | 둘 다 성공 |
| 동시성 | 같은 이메일 동시 가입 | UNIQUE 제약 위반 감지 | 하나는 409 |
| DB | 연결 실패/타임아웃 | 짧은 재시도 후 실패 | 503/500 + 알림 |
| 외부 | 동기화 중 외부 API 429/5xx/타임아웃 | 지수 백오프 재시도, 한도 보호, 일부 실패 시 `partial` 기록 | (사용자 영향 없음) |
| 외부 | 소스 응답 스키마 변경 | 어댑터에서 검증 실패 → 해당 항목 건너뛰고 기록, 기존 데이터 유지, 운영 알림 | - |
| 외부 | 소스에서 카드 소멸 | 삭제 금지, `is_active=false` | - |
| 시스템 | 처리되지 않은 예외 | 전역 핸들러가 500 반환, 상세는 서버 로그 | 500 `INTERNAL_ERROR` |

### 1.3 동기화 작업(FR-DATA) 예외 정책
- **원자성 단위는 세트**: 한 세트의 카드는 트랜잭션으로 반영 (중간 실패 시 해당 세트만 롤백, 이전 데이터 유지)
- 중복 실행 방지: 이미 `running` 상태 작업이 있으면 새 작업 시작 거부(락)
- 일일 호출 예산 상한 설정 (예: 한도의 50%까지 사용), 초과 시 중단하고 다음 주기에 이어서
- 실패 알림: `failed`/`partial` 상태 발생 시 운영자에게 통지 (수단은 DEC-06 이후)

### 1.4 클라이언트 측 예외 시나리오

| 상황 | UI 처리 |
|------|---------|
| 네트워크 없음/타임아웃 | 목록: 오류 + 다시 시도. 보유 토글: 롤백 + 토스트 |
| 401 `TOKEN_EXPIRED` | 자동 refresh 후 원 요청 1회 재시도 (동시 요청은 refresh를 한 번만 수행하도록 직렬화) |
| refresh 실패 | 세션 삭제 → 로그인 화면 (원래 화면 복귀 정보 보관) |
| 429 | `Retry-After`를 존중해 자동 재시도 또는 안내 |
| 5xx/503 | "잠시 후 다시 시도해 주세요" + 재시도 |
| 이미지 로드 실패 | 플레이스홀더 + 탭 재시도 |
| 검색 결과 0건 | 빈 상태 화면 |
| 응답 필드 누락/예상 밖 값 | 방어적으로 처리(이름 없음 등 대체 표시), 크래시 금지 |
| 연속 빠른 토글 | 같은 카드의 요청은 순서 보장(큐잉) 또는 마지막 의도 우선으로 병합 |
| 앱 강제 종료 중 요청 | 서버 상태가 진실의 원천. 재실행 시 목록 재조회로 일치 |

### 1.5 사용자 메시지 (예시, 리소스 파일로 관리)
| code | 문구 |
|------|------|
| INVALID_CREDENTIALS | 이메일 또는 비밀번호가 올바르지 않아요. |
| EMAIL_ALREADY_EXISTS | 이미 가입된 이메일이에요. |
| RATE_LIMITED | 요청이 너무 많아요. 잠시 후 다시 시도해 주세요. |
| (네트워크) | 인터넷 연결을 확인해 주세요. |
| INTERNAL_ERROR / 503 | 문제가 발생했어요. 잠시 후 다시 시도해 주세요. |
| 보유 저장 실패 | 저장하지 못했어요. 다시 시도해 주세요. |

## 2. 보안 설계

### 2.1 위협 모델 요약

| 자산 | 위협 | 대응 |
|------|------|------|
| 계정 자격 증명 | 무차별 대입, 크리덴셜 스터핑, DB 유출 | 강한 해시, 레이트 리밋, 계정 존재 여부 비노출 |
| 세션 토큰 | 탈취, 재사용 | 짧은 access 수명, refresh 회전/재사용 감지, 보안 저장소 |
| 사용자 보유 데이터 | 타인 접근(IDOR) | `/users/me` 설계, 서버 측 소유자 검증 |
| 외부 API 키 | 앱 번들/로그 유출 | 서버 환경 변수 전용 (NFR-SEC-02), 앱에 미포함 |
| 서버/DB | 인젝션, 설정 오류 | 파라미터 바인딩, 최소 권한, 비밀 관리 |
| 개인정보(이메일) | 유출, 과다 수집 | 수집 최소화, 탈퇴 시 삭제, 로그 마스킹 |
| 가용성 | 크롤링/DoS | 레이트 리밋, 페이지 크기 상한, 캐시 |

### 2.2 인증/세션 (DEC-04 후보 중 "이메일+비밀번호" 기준 제안)

| 항목 | 설계 |
|------|------|
| 비밀번호 저장 | 느린 적응형 해시(Argon2id 우선 검토, 또는 bcrypt) + 솔트. 평문/가역 암호화 금지 |
| 비밀번호 정책 | 최소 8자, 이메일과 동일 금지. (P1: 유출/흔한 비밀번호 차단) |
| 토큰 | access 토큰 수명 **15분**, refresh 토큰 수명 **30일** [제안], refresh는 **회전**(사용 시 새 토큰 발급·이전 폐기) |
| refresh 저장 | 서버에는 **해시만** 저장, 클라이언트는 OS 보안 저장소 |
| 로그아웃 | 해당 refresh 폐기 |
| 비밀번호 재설정 | 1회용·단기(예: 30분) 토큰, 사용 후 모든 세션 폐기, 요청 응답은 계정 존재 여부와 무관하게 동일 |
| 로그인 보호 | 로그인 엔드포인트: IP당 분당 N회(예: 10), 계정당 연속 실패 시 점진적 지연 |
| 오류 메시지 | 로그인 실패 사유 통합("이메일 또는 비밀번호") |
| 서명 키 | 환경 변수/시크릿 관리, 주기적 교체 가능한 구조 |

> BaaS 인증(DEC-04/DEC-02)을 선택하면 위 항목 중 상당수가 제품 기능으로 대체되며 설정 검토로 바뀐다.

### 2.3 전송 및 저장
- **전 구간 HTTPS(TLS)** 강제. HTTP 요청은 거부/리디렉션. HSTS는 웹 확장 시 적용
- Android: 클리어텍스트 트래픽 차단(`usesCleartextTraffic=false` 수준의 설정), 디버그 빌드 예외 분리
- 토큰은 앱 일반 저장소(SharedPreferences 평문 등)에 저장 금지 → 보안 저장소 사용
- DB 접속 정보, JWT 서명 키, 외부 API 키는 **저장소에 커밋 금지**, 환경 변수/시크릿 매니저
- DB 저장 데이터 암호화(디스크 암호화)와 백업 암호화는 호스팅 환경(DEC-06)에서 제공 여부 확인

### 2.4 입력 검증 및 인젝션 방어
- 모든 요청 파라미터 서버 측 검증 (타입, 길이, 허용 값 목록: `sort`, `owned`, `order`)
- DB 접근은 **파라미터 바인딩/ORM** 사용. 문자열 연결로 SQL 조합 금지 (검색어 `q`, 필터 값 포함)
- LIKE 검색어의 와일드카드(`%`, `_`) 이스케이프
- 정렬 컬럼은 **허용 목록 매핑**으로만 사용 (사용자 입력을 컬럼명으로 직접 사용 금지)
- 요청 본문 크기 제한, `limit` 상한(100)
- 커서는 서명 또는 무결성 검증 후 해석 (변조 방지)

### 2.5 접근 제어
- 사용자 데이터 API는 경로에 사용자 ID를 포함하지 않고 `/users/me` 만 사용 (IDOR 방지)
- 모든 쓰기/개인 데이터 API는 인증 필수. 공개 API는 읽기 전용 카드 데이터만
- 동기화/운영 기능은 **공개 엔드포인트로 노출하지 않음** (05 문서 §5)
- DB 계정은 용도별 최소 권한 (앱용: DML만, 마이그레이션용: DDL 별도)

### 2.6 남용 방지
| 대상 | 제안 한도 |
|------|-----------|
| 로그인/가입/재설정 | IP당 분당 10회 내외, 초과 시 429 |
| 카드 조회(게스트) | IP당 분당 120회 내외 (크롤링 완화) |
| 보유 변경(로그인) | 사용자당 분당 120회 내외 |
| 요청 크기 | 본문 최대 수 KB |

### 2.7 개인정보 보호
| 항목 | 설계 |
|------|------|
| 수집 항목 | 이메일(필수), 표시 이름(선택), 보유 기록. 그 외 수집 안 함(최소 수집) |
| 이용 목적 | 계정 식별, 보유 기록 동기화 |
| 보관/삭제 | 탈퇴 시 즉시 삭제(CASCADE). 로그에는 이메일을 마스킹하거나 기록하지 않음 |
| 동의 | 가입 시 약관·개인정보처리방침 동의 + 시각 저장 |
| 제3자 제공 | 없음. 단, 크래시/분석 도구(DEC-15) 도입 시 처리방침에 명시 |
| 연령 | 타깃 연령 미확정(DEC-13). 아동 대상 가능성이 있으면 별도 정책(만 14세 미만 등 법적 기준) 검토 필요 |
| 법규 | 개인정보 보호 관련 국내외 법규 적용 여부는 서비스 대상 국가 확정 후 확인 (법률 자문 권장) |

### 2.8 로깅/모니터링
- 구조화 로그, `requestId` 상관관계, 보안 이벤트(로그인 실패 급증, refresh 재사용 감지, 429) 기록
- **금지**: 비밀번호, 토큰, API 키, 전체 이메일 로그 기록
- 동기화 작업 결과(`sync_jobs`) 및 실패 알림, 헬스체크
- 크래시 리포트: 개인정보 마스킹 (DEC-15)

### 2.9 의존성/공급망
- 의존 라이브러리 취약점 점검 (자동화된 의존성 감사), 잠금 파일 커밋, 정기 업데이트
- CI에서 비밀 값 스캔(커밋된 키 탐지)

### 2.10 Android 앱 보안
- 릴리스 빌드: 코드 난독화/축소 설정 검토, 디버그 로그 제거
- 외부 API 키/서버 비밀을 앱에 포함하지 않음 (앱에 들어가는 값은 공개 가능한 값만)
- 백업 정책: 민감 토큰이 클라우드 백업에 포함되지 않도록 설정
- 앱 서명 키 안전 보관 (Play 앱 서명 사용 검토)

## 4. 지식재산권(IP) 및 외부 소스 이용 리스크 (R-01 상세)

- 카드 이미지·캐릭터·명칭은 권리자 소유이며, Pokémon TCG API는 커뮤니티 제공 데이터다. **비상업적 포트폴리오**와 **스토어 상업 출시**는 위험 수준이 다르다.
- 출시 전 해야 할 일 **[제안]**
  1. Pokémon TCG API 이용 약관과 데이터/이미지 사용 조건 확인
  2. 권리자(The Pokémon Company 등)의 팬 콘텐츠/이용 가이드라인 확인
  3. 1차는 무광고로 확정(DEC-14). 수익화가 생기면 위험 증가
  4. 필요하면 법률 자문
- 이 항목은 **개발 착수를 막지 않지만 출시 게이트(Release Gate)** 로 09 문서에 포함한다.

## 4.1 IP 리스크 보강 (2차 조사 결과)
- 2차 조사에서 권리자가 **IP 사용 허가 요청 자체를 받지 않는다**고 밝힌 점이 확인되었다 (11 §1). 따라서 위 "출시 전 해야 할 일"의 3번(권리자 가이드라인 확인)은 **허가를 받는 절차가 아니라 위험 수용/회피 결정**에 가깝다.
- 이미지를 DB로 복제하지 않고 표시 전용 URL로 두면, 신고 접수 시 이미지 표시를 즉시 끌 수 있고(원격 설정 플래그) 데이터 약관 위반 위험도 줄어든다 (ADR-11).

## 6. Supabase 기반 보안 설계 (2차 갱신)

> 인증·세션·비밀번호 해시는 Supabase Auth가 담당하므로 §2.2의 직접 구현 항목은 **"설정 검토"** 로 대체된다. 대신 **RLS가 유일한 데이터 접근 방어선**이 되어 중요도가 가장 높다.

### 6.1 RLS (최우선)
- **모든 `public` 테이블에 RLS 활성화**. RLS가 꺼진 테이블은 publishable 키만 있으면 누구나 읽고 쓸 수 있다 (Supabase 프로덕션 체크리스트).
- 정책 표는 04 §9.3. 카드/세트/희귀도: 읽기 공개·쓰기 정책 없음. `user_cards`/`profiles`: `auth.uid()` 본인만. `sync_jobs`: 정책 없음(접근 불가).
- 정책/함수 추가 후 `get_advisors`(보안/성능 권고)로 RLS 누락과 위험한 함수를 점검, 결과를 PR에 첨부.
- RPC 함수는 기본 `security invoker`로 작성해 RLS를 그대로 적용. `security definer`가 꼭 필요하면 `search_path` 고정과 입력 검증을 필수로 한다.

### 6.2 키 관리
| 키/비밀 | 위치 | 앱 포함 |
|---------|------|---------|
| Supabase URL, publishable(anon) 키 | 앱 설정 | 가능 (RLS가 보호) |
| service role 키 | Edge Function 환경(자동 주입) | **금지** |
| 데이터 소스 API 키 | Edge Function Secrets | **금지** |
| SMTP 자격 증명 | Supabase Auth SMTP 설정 | **금지** |
| `pg_cron`이 Edge Function 호출 시 쓰는 키 | Supabase Vault | **금지** |
- 저장소에는 `.env`류를 커밋하지 않고 `.env.example`만 둔다. CI에서 비밀 값 스캔(PH-1 T-105).

### 6.3 Auth 설정 체크
- 이메일 확인 **활성화**, OTP/링크 만료는 1시간 이하 권장.
- **커스텀 SMTP** 사용(발송 제한, 도메인 신뢰도). 링크 추적 기능은 꺼야 확인 링크가 깨지지 않는다.
- 비밀번호 최소 길이/복잡도 정책 설정, 가입·재설정에 **CAPTCHA** 적용 검토(봇 방지).
- Auth 속도 제한 기본값(가입·재설정 60초 간격, 토큰 갱신 IP당 시간당 1800회 등) 확인 후 필요 시 조정.
- 이메일 스캐너가 링크를 먼저 열어 단일 사용 링크가 소진되는 문제 대비(중간 확인 페이지) — 재설정 UX 테스트 항목.
- Supabase **계정 자체**(프로젝트 소유자)에 MFA 활성화.

### 6.4 공개 RPC 남용 방지
- 게스트가 호출 가능한 `list_cards`/`get_card`는 공개 API이므로: `lim` 상한 100, 검색어 길이 제한(예: 50자), 정렬 허용 목록, LIKE 와일드카드 이스케이프, 비용 큰 `total` 계산은 옵션으로만.
- 크롤링 방어는 기본 제공되지 않는다. 트래픽이 커지면 CDN/캐시 또는 Edge Function 앞단 레이트 리밋 도입 검토(비용·복잡도 trade-off). 카드 데이터 자체는 공개 정보이므로 위험은 주로 **가용성·비용**이다.

### 6.5 Edge Function 보안
- `sync-catalog`: 사용자 JWT가 아닌 **전용 시크릿 헤더/서비스 키 검증**으로만 호출 허용(공개 호출 시 외부 API 한도 소진 위험).
- `delete-account`: 호출자의 JWT를 검증하고 **자기 자신의 계정만** 삭제, 비밀번호 재확인 후 수행. 삭제 후 FK CASCADE로 `profiles`, `user_cards`가 삭제되는지 테스트.
- 로그에 이메일/토큰/비밀 출력 금지. 한도: CPU 2초/요청, 벽시계 150초(무료)/400초(유료) → 동기화는 세트 단위 분할.

### 6.6 광고·분석 SDK (DEC-14/15/17)
- **1차는 광고 SDK를 넣지 않는다.**
- 분석/크래시 SDK(DEC-15)를 넣을 때는 가족 정책(연령 확인 전 AAID 미전송 등)과 개인정보처리방침에 맞는지 **도입 전 검증**.
- 아동 포함 앱은 인증되지 않은 SDK/API를 통한 **로그인 강제 금지** 규정이 있으므로, 로그인 경로에 비인증 서드파티 SDK(예: 소셜 로그인 SDK)를 넣는 설계는 사전 검토 필요(현재는 Supabase Auth 이메일 로그인만 사용).
